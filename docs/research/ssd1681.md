## 1. Executive summary and the open risks
- Controller: SSD1681, 200 source x 200 gate, 2 x 200x200-bit RAM (BW 0x24, RED 0x26), internal OSC, booster control
  (external FET circuit, present on the board), OTP with 36 waveform sets keyed by temperature, internal temperature
  sensor. Panel: GDEY0154D67, 200x200, active area 27.0 x 27.0 mm, outline 31.80 x 37.32 x 1.0 mm, VCI 3.0 V typ.
  [SSD-DS 1, 2; GD-SPEC 1, 3, 4]. Wired on this board for 4-wire SPI (BS1 = GND), see hardware.md section 8.
- **Open risk #1 (UNSPECIFIED): partial/"no-flicker" update.** The GD spec quotes "partial update 0.26 s, no flicker"
  [GD-SPEC 7-2] but **neither document publishes a partial waveform, LUT bytes, or the command sequence.** The SSD1681
  provides the building blocks (0x32 LUT write, 0x22 "display mode 2" values, 0x37 per-waveform mode bits) and nothing
  more. Whether this panel's OTP already holds a display-mode-2 waveform is unknowable from documents; section 11 gives a
  spec-grounded way to find out (read OTP bits via 0x2D) and a decision rule. A custom LUT cannot be derived from the
  documents (they do not say which of VSH1/VSL drives black or white). Worst case needs the panel vendor's reference
  waveform, whose licence would need the owner's approval; I did not use any.
- **Open risk #2: SPEC vs vendor guidance.** GD says: at least **180 s between display updates**, and a **full refresh
  after every 5 partial updates** [GD-USE; GD-SPEC 7-2 note]. SPEC wants a partial update every 60 s and a rarer full
  refresh. Both are deliberate deviations (3x the minimum update rate; N larger than 5): make "partials between full
  refreshes" (default 10, vendor value 5) and the update interval settings, and log the deviation as tech debt.
- **Open risk #3: operating range 0 to +50 C** [GD-SPEC 7-1, drawing]: a watch worn outdoors in winter leaves it. Update
  waveforms are temperature-selected from OTP and the SSD1681 will not update at all if no OTP range matches the sensed
  temperature [SSD-DS 6.9]. Read the temperature, log it, never hang on BUSY (section 9 timeouts).
- **Contradiction (deep-sleep RAM retention):** SSD1681 says deep-sleep mode 1 **retains** RAM (1 uA typ) and mode 2 does
  not (0.7 uA typ) [SSD-DS 10, Table 10-1]; GD's table lists "deep sleep 1 uA typ, 5 uA max, RAM data **not** retained"
  without naming a mode [GD-SPEC 7-2]. Do not rely on retention: rewrite both RAMs on every update (cheap, section 9).
- **Contradiction (minor, harmless):** GD's operating-flow figure fills "RAM 0x24" with 0x46 and "RAM 0x26" with 0x47; the
  SSD1681 command table says 0x46 = RED RAM (0x26) and 0x47 = BW RAM (0x24) [GD-SPEC 12.1 vs SSD-DS 7]. Both get the same
  value (0xF7), so no effect; follow the SSD1681 table.
- Good news: the display's energy is small. Typ operating current 1.5 mA at 3.0 V (4.5 mW); full 2 s, fast 1.5 s,
  partial 0.26 s at 25 C [GD-SPEC 7-2]. One partial update is about 0.4 mC (0.11 uAh); 1,440 per day is about
  0.16 mAh/day (derived). MCU awake time will dominate battery life, not the panel.

## 2. Interface, SPI, pins, BUSY
- Bus: 4-wire SPI (BS1 low = 8-bit SPI with D/C#) [SSD-DS Table 6-1/6-2; GD-SPEC Note 5-5]. Write: SDA sampled on **rising
  SCL edge, MSB (D7) first**; D/C# must be stable for the whole byte: D/C# low = command byte, high = data byte; CS# low for
  the transfer. VERIFIED [SSD-DS 6.1.2].
- SCL idle level: not stated in text; the vendor timing diagram shows SCL low while CS# is low and before the first rising
  edge, so **SPI mode 0 (CPOL 0, CPHA 0)** [GD-SPEC Fig 7-5]. Mode 3 also meets the stated rising-edge sampling; use mode 0.
- Max write clock **20 MHz**; read mode 2.5 MHz [SSD-DS Table 11-1, section 2]. Timing (write): CS# low to first SCL rising
  60 ns, CS# hold after last falling edge 65 ns, CS# high between transfers 100 ns, SCL high/low 25 ns each, data setup 10 ns,
  hold 40 ns. Recommend **10 MHz** (half of max, margin on long traces; ASSUMED): a 5,000-byte plane takes about 4 ms.
  GD's own timing table (Table 7-4) is an image without values in the PDF; the SSD1681 table is the source.
- **No MISO on this board**: panel SDA (GPIO48) is the only data line. Reads (commands 0x1B, 0x27, 0x2D, 0x2E, 0x2F, 0x35)
  would need a bit-banged turnaround on GPIO48 at <= 2.5 MHz; none are needed for normal operation.
- Supply: VCI 2.2-3.7 V (VDDIO must equal VCI) [SSD-DS 10]; GD abs max VCI -0.5..+4.0 V [GD-SPEC 7-1]. 3.3 V board rail is in range.
- **BUSY (GPIO36): HIGH = busy**; while high no command may be issued and the operation must not be interrupted [SSD-DS Table
  5-2; GD-SPEC Note 5-4, Rev 1.1 corrected this from "low" to "high"]. BUSY is high during: waveform output (0x20), SW reset
  (0x12), auto-fill RAM (0x46/0x47), OTP operations, temperature-sensor exchange, VCOM sense, HV/VCI detect. **After deep
  sleep (0x10) BUSY stays high** [SSD-DS 0x10]: never wait for BUSY low after 0x10; only a hardware reset wakes the chip.
- Reset: RES# active low. **Reset pulse width and post-reset BUSY time are UNSPECIFIED.** The vendor flow says: power VCI, wait
  10 ms; HW reset; SW reset (0x12); wait 10 ms [SSD-DS 8.1; GD-SPEC 12.1]. Use RES# low >= 10 ms then high, wait >= 10 ms
  (ASSUMED, generous) then 0x12 and wait BUSY low.
- Board facts that matter (hardware.md 8): VCI/VDDIO always powered, RES# held high by a 100K pull-up while the MCU sleeps,
  temperature-sensor pins TSCL/TSDA unconnected.

## 3. RAM layout, windows, data entry, orientation
- Two RAM planes, each 200 x 200 bits = **5,000 bytes**, **25 bytes per row** (200/8, no padding); X address unit = 1 byte =
  8 pixels (0..0x18); Y address = gate line (0..0xC7) [SSD-DS 6.5; 0x44/0x45/0x4E/0x4F].
- Pixel polarity (B/W panel): **BW RAM bit 1 = white, 0 = black** [SSD-DS 0x24 text, Table 6-5]. In Table 6-5 the RED bit is
  a don't-care for a B/W panel in the shown mapping (R=1 maps to the same colours as R=0). VERIFIED. Define the framebuffer
  with 1 = white so it can be copied to the panel unchanged.
- Bit order inside a byte (which bit is the left-most pixel): **UNSPECIFIED** in the text. Expect D7 = lowest X for X-increment
  (ASSUMED); confirm with the asymmetric test pattern in section 11 (E3).
- Data entry 0x11, parameter A: bits[1:0] ID = 00 Y-dec/X-dec, 01 Y-dec/X-inc, 10 Y-inc/X-dec, **11 Y-inc/X-inc (POR)**;
  bit2 AM: 0 = address counter advances in X first (POR), 1 = Y first. POR A = 03. VERIFIED [SSD-DS 0x11].
- Window: 0x44 [XSA, XEA] 6-bit byte addresses (POR 00, 15); 0x45 [YSA lo, YSA hi(bit0=A8), YEA lo, YEA hi] 9-bit (POR 000,
  127). Full 200x200 window: 0x44 = 00 18; 0x45 = 00 00 C7 00. Counters: 0x4E [X], 0x4F [Y lo, Y hi]. With a decrementing
  direction start > end (e.g. Y: start C7 end 00). Behaviour on writing past the window end (wrap) is UNSPECIFIED: write
  exactly the window's byte count. Windows must be byte aligned in X (multiples of 8 pixels).
- **Display update acts on the whole panel**, the window only limits RAM writes (UNSPECIFIED in text; standard for this
  controller family, ASSUMED). Therefore keep both planes complete and consistent: write full frames to both RAMs every
  update (10 KB, about 8 ms at 10 MHz) instead of windows. A window is an optional optimisation.
- Which RAM holds what: full update (display mode 1): 0x24 = new image; 0x26 ignored for B/W (Table 6-5) but we also load it
  with the same image so it is a valid "previous image" for the next partial. Partial update (display mode 2): **ASSUMED**
  0x24 = new image, 0x26 = previous image (LUT index = {RED bit, BW bit}); not stated in the documents; experiment E2 verifies,
  swap planes if transitions come out inverted. 0x21 can bypass/invert a plane (A[7:4] red, A[3:0] BW: 0 normal, 4 bypass as 0,
  8 inverse), POR 00. Optional RAM ping-pong for display mode 2 exists via 0x37 byte F bit 6 (POR off): not used.
- **Physical orientation: UNSPECIFIED.** The GD drawing marks no G0/S0 corner [GD-SPEC 4]. Known from the board: panel FPC and
  its wide bezel sit at the **bottom (6 o'clock)** of the watch (PCB connector placement; SQFMI FAQ: "white bezel at the
  bottom") [PCB; DOCS-FAQ]. Source lines (200, X) run across the width, gate lines (200, Y) down the height. Choose the
  mapping once, in one constant (0x11 value + 0x01 byte B [GD/SM/TB] + framebuffer bit order), and settle it with E3 on first
  light; lock it with a hardware golden-image test. 0x01 B bits: GD (first gate), SM (interlace), TB (0 = scan G0..G199,
  1 = reverse): POR 00 [SSD-DS 0x01]; TB = 1 mirrors vertically, 0x11 ID bits mirror/rotate the write direction.
- Memory budget: framebuffer 5,000 bytes; a "previous frame" copy is another 5,000 bytes. ESP32-S3 RTC slow memory is 8 KB,
  so holding the previous frame there leaves about 3 KB (architecture decision for later; alternative: re-render the previous
  minute from stored state).

## 5. 0x22 update-control values
The datasheet lists 12 values [SSD-DS 0x22]. They decompose consistently as a bit-field (the decode is my inference;
only the 12 listed values are documented): b7 enable clock, b6 enable analog, b5 load temperature, b4 load LUT (from OTP),
b3 display mode (0 = mode 1, 1 = mode 2), b2 run display, b1 disable analog, b0 disable OSC/clock.

| Value | Sequence | Use |
|---|---|---|
| F7 | clock, analog, load temperature, load LUT, **display mode 1**, power down | **full refresh** (single-shot) |
| FF | same with **display mode 2** (POR value) | partial candidate (OTP mode-2 waveform) |
| C7 / CF | like F7 / FF but **no** temperature or LUT load | only after a LUT/temperature is already loaded in this wake |
| B1 / B9 | load temperature + LUT (mode 1 / mode 2) only, no display | pre-load, then C7/CF |
| 91 / 99 | load LUT only (mode 1 / mode 2) | with a manually written temperature (0x1A) |
| 80 / C0 / 01 / 03 | enable clock / clock+analog / disable clock / disable analog+clock | manual power stages |

- **Do not leave 0x22 at POR (FF) by accident:** it would run display mode 2 plus temperature load. Always write 0x22
  immediately before 0x20.
- Combinations that keep analog on after the update (e.g. clearing b1/b0) are undocumented: do not use.

## 6. Waveform/LUT facts, temperature sensing, border
- Waveform storage: 159-byte waveform setting (WS) = bytes 0-152 via **0x32 (153 bytes)**, byte 153 EOPT via 0x3F, 154 VGH via
  0x03, 155-157 VSH1/VSH2/VSL via 0x04, 158 VCOM via 0x2C [SSD-DS 6.7, Fig 6-6]. Structure: 5 LUTs (LUT0-4), 12 groups x 4 phases
  (A-D), per phase voltage selector VS (2 bits: 00 VSS, 01 VSH1, 10 VSL, 11 VSH2 [VCOM: DCVCOM / VSH1+ / VSL+]), phase length
  TP 0-255 frames, group repeat RP 1-256, state repeat SR 1-256 (A/B and C/D), frame rate FR 0-7, XON all-gate-on flags
  [6.6, 6.7]. Frame rate adjustable 25-200 Hz (section 2 features).
- LUT index for B/W: {RED bit, BW bit} = 00 LUT0 (black), 01 LUT1 (white), 10 LUT2 (= LUT0), 11 LUT3 (= LUT1) [Table 6-5]. This is
  the *display mode 1* picture. How LUT2/LUT3 are used in display mode 2 is UNSPECIFIED.
- OTP holds 36 WS and 36 temperature ranges; selection: sense temperature (12-bit), search TR0..TR35, **last match wins**, range
  criterion lower < T <= upper, and the match depends on the per-WS display-mode bit [6.9]. Datasheet example ranges: <=5, 5-10,
  10-15, 15-20, 20-25, 25-30, 30-35, >33 C (example only; real OTP content for this panel is UNKNOWN). **Precaution (verbatim in
  spirit): if no range matches, the panel does not update** [6.9].
- **Temperature handling for this board:** POR sensor select is external (0x18 = 48) and TSCL/TSDA are unconnected, so
  **write 0x18 = 80 (internal sensor) after every reset**. Internal accuracy +-2 C from -25 to 50 C [6.8.1]. If the update
  sequence does not load a temperature (C7/CF), the register keeps its POR 7FF (127.9 C) and selects the hottest waveform: never
  rely on that. Alternative: write 0x1A yourself (e.g. from another sensor), then use 91/99 + C7/CF.
- Border (VBD) 0x3C, POR C0 = Hi-Z: A[7:6]: 00 = follow waveform (GS transition), 01 = fixed level, 10 = VCOM, 11 = Hi-Z;
  A[5:4] fixed level 00 VSS, 01 VSH1, 10 VSL, 11 VSH2; A[2] GS-transition control (0 follow LUT with VCOM at RED, 1 follow LUT);
  A[1:0] which LUT the border follows (00..11 = LUT0..3) [SSD-DS 0x3C]. Candidates (derived from the table, visual result
  UNVERIFIED): **full refresh 05** (follow LUT1 = white border, flashes with the panel), **partial 80** (border held at VCOM, no
  border transition). Verify on hardware (E4).
- Custom VCOM: GD notes VCOM should be within +-0.1 V of the module's assigned value [GD-SPEC 7-2 note]; the assigned value is not
  printed in the PDF text (UNSPECIFIED; module label/FPC). With OTP-loaded waveforms VCOM comes from OTP; do not override.

- Always end an update with 0x10; without it the controller idles at about 20 uA (vs 1 uA) for the whole minute.

- Time awake budget idea: the vendor flow needs only SPI traffic (about 10 KB) plus the BUSY wait; the BUSY wait can be spent

## 8. Panel lifetime and handling constraints
Sources: GD usage guidelines [GD-USE], GD spec [GD-SPEC 7, 11, 14, 16]. The spec is **silent on a guaranteed refresh-cycle
lifetime** (no "N million refreshes" figure) and on the maximum number of partial updates.
- **Minimum interval between display updates: 180 s** "for extended lifespan" [GD-USE]. (CONFLICT with 60 s watch ticks.)
- **Full update after every 5 partial/fast updates** to limit after-images [GD-USE; GD-SPEC 7-2 note 2].
- Full update at least once per 24 h is stated for multi-colour/full-colour panels; the page is silent for B/W. Adopt 24 h as a
  floor anyway (a ticking watch exceeds it trivially). For storage over 6 months: refresh every 3 months [GD-USE].
- Put the panel in deep sleep between updates, especially for long idle times [GD-USE]. "Battery low detection and auto-update to
  full white" is recommended for product design [GD-USE]: for the critical-battery screen consider ending on a white (or minimal)
  frame before the device dies; storing a white image avoids inerasable ghosting (ASSUMED applicable to B/W).
- Never interrupt an update (BUSY high): do not reset the panel, cut its supply, or deep-sleep/brown out the MCU mid-update [SSD-DS
  0x20; GD-SPEC Note 5-4]. After any aborted update mark the "previous image" invalid and do a full refresh next.
- Operating temperature 0 to +50 C; storage -25 to +70 C; optimal storage humidity 55 +-10 %RH; qualification at 0 C and 50 C
  [GD-SPEC 7-1, 11]. Storage conditions (GD-USE): 23 +-3 C, 55 +-10 %RH, front up, white pattern.
- Mechanical/ESD: glass breaks; do not press the panel; do not plug/unplug the FPC while powered; do not touch the IC bonding
  area; ESD +-4 kV contact incl. the IC/FPC area [GD-SPEC 11, 16].
- Ghosting mitigation (all ASSUMED unless stated): full refresh cadence setting (vendor 5); always give the previous frame to a
  partial update (do not partial-update from an unknown state); keep updated regions small (digits only) by drawing static
  elements identically every frame; full refresh at boot, after any abnormal reset and when temperature changes by more than
  about 10 C; keep large static black areas out of the face; perform the daily full refresh at a quiet time (e.g. midnight).

## 9. Recommended sequences
Notation: `cmd(data...)`. "wait" = wait for BUSY low. Quartz keeps a full-frame 1-bpp framebuffer (5,000 bytes, 1 = white).
Tags: [S] = taken from the datasheet flow/table, [A] = my assumption to verify (section 11). Timeouts are ASSUMED fail-safes: on
timeout hard-reset the panel, mark previous image invalid, force a full refresh next wake.

### 9.1 Common start (every wake that updates the panel)
1. Pulse RES# low >= 10 ms, high, wait >= 10 ms. [A: timing not specified]
2. `12` (SW reset); wait (timeout 200 ms). [S: flow 8.1]
3. `01(C7 00 00)`, `11(03)`, `44(00 18)`, `45(00 00 C7 00)`. [S]
4. `18(80)` internal temperature sensor. [S: 0x18; needed because TSCL/TSDA are unconnected]
5. `0C(8B 9C 96 0F)` soft start (POR values written explicitly; flow 8.1 includes this step). [S]

### 9.2 Full refresh (display mode 1, OTP waveform) -- clears ghosting, flashes, about 2 s
1. Common start 9.1 (steps 1-5).
2. `3C(05)` border follows white LUT. [S table, effect A]
3. `4E(00)`, `4F(00 00)`, `24` + 5,000 bytes (new image). [S]
4. `4E(00)`, `4F(00 00)`, `26` + 5,000 bytes (same image; becomes the base for the next partial). [A]
5. `22(F7)`, `20`; wait (typ 2 s; timeout 10 s). [S]
6. `10(01)`; do **not** wait for BUSY. [S]
7. Bookkeeping: previous := new; partial_count := 0; last_full_time := now.
(GD's flow additionally pre-fills both RAMs with `47(F7)` / `46(F7)` after reset and waits for BUSY; redundant when full frames
are written, optional for a first-light "clear to white".)

### 9.3 "Show the new minute without visible flicker" (display mode 2, no flash)
Pre-conditions: panel last showed image `prev` (all 5,000 bytes known), `partial_count < N`, last update >= configured interval,
sensed temperature in 0-50 C.
1. Common start 9.1 (steps 1-5).
2. `3C(80)` border held at VCOM. [S table, effect A]
3. `4E(00)`, `4F(00 00)`, `26` + `prev` (previous image, 5,000 bytes). [A: RED = previous in mode 2]
4. `4E(00)`, `4F(00 00)`, `24` + `next` (new image). [A]
5. `22(FF)`, `20`; wait (typ 0.26 s; timeout 5 s). FF = load temperature + load LUT (display mode 2 from OTP) + display + power down. [S value; whether OTP has a mode-2 waveform: UNSPECIFIED]
6. `10(01)`; do not wait.
7. Bookkeeping: prev := next; partial_count++; if partial_count >= N, the next update is 9.2.
If section 11 shows the OTP has no usable mode-2 waveform (E1), the fallback needs a custom LUT: after step 2 write `32` + 153
bytes, `3F(02)`, `03(VGH)`, `04(VSH1 VSH2 VSL)`, `2C(VCOM)` and use `22(CF)` (no temperature/LUT load). **Not shippable from the
documents: LUT bytes are not published.**

### 9.4 Cold boot / abnormal reset
Any boot other than a clean deep-sleep wake with a valid previous-frame record: run 9.2 (full refresh) first.

### 9.5 Timeouts and failure handling (all ASSUMED)
BUSY wait: SW reset 200 ms; partial 5 s; full 10 s (cold panels slow down); poll BUSY at 1-5 ms or wait on the GPIO edge. On timeout:
abort, reset panel, invalidate previous image, count the fault in diagnostics, never block the watch face.

## 10. Rules a host-side fake controller can enforce
Derived from the sections above; each can fail a unit test.
1. SPI: mode 0, MSB first, <= 20 MHz, CS# low around every byte group, D/C# stable per byte, 100 ns CS# high between transfers.
2. State machine: Reset -> Idle -> {Command, Data stream} ; BUSY high after 12, 20, 46, 47; **commands/data while BUSY high = fail**.
3. After `10(01|11)`: BUSY stays high; every SPI byte until a RES# low pulse = fail; RES# pulse returns to Idle with all registers at
   POR and RAM contents UNDEFINED (mode 1 retained is not guaranteed by GD).
4. `12` restores POR registers except 0x10, keeps RAM; `RES#` restores POR registers.
5. Parameter counts: 01:3, 03:1, 04:3, 0C:4, 10:1, 11:1, 18:1, 1A:2, 21:2, 22:1, 32:153, 3C:1, 3F:1, 44:2, 45:4, 4E:1, 4F:2, 46:1, 47:1.
6. Ranges: 44: XSA/XEA <= 0x18; 45: Y <= 0xC7; 4E <= 0x18; 4F <= 0xC7; 01 gate count = A+1 = 200; 11 <= 07; 3C reserved bits.
7. RAM writes: exactly 25 x rows bytes for the programmed window; overflow = fail; write order 4E/4F before 24/26.
8. 0x20 requires a 0x22 value written in the same wake (reject POR-FF use), a valid temperature path (0x18 = 80 or a 0x1A write
   when the sequence loads a temperature) and, for display mode 2, both planes written since the last reset.
9. Reject use of 0x18 = 48 (external sensor) on this board; reject 08/2A/30/36/39 (OTP program) entirely.
10. Image model: FULL (F7): panel image := BW RAM. PARTIAL (FF/CF): changed pixels derived from (RED old, BW new), unchanged pixels
    keep state; record partial_count and flag > N and < 180 s since last update as policy warnings (not hard faults).
11. Deep sleep must be issued before the watch sleeps; flag a wake cycle that ends without 0x10 (20 uA waste).

## 11. Bring-up experiments
Run in order on the first unit; each result fixes an UNSPECIFIED item. Console commands should expose raw command/data writes.
- **E1 (is there a mode-2 waveform?)** Read OTP option bytes with `2D` (bit-banged read on GPIO48, <= 2.5 MHz; first byte after the
  command may be dummy per section 4 text for 0x27, check): bytes C..G are display-mode bits for WS0..35 (1 = mode 2), H..K waveform
  version. If any WS has mode 2 and the TR ranges cover 0-50 C, plan 9.3 as written. If all zero, only a custom LUT can give partial
  updates: stop and ask the owner about the vendor reference waveform.
- **E2 (RAM roles in mode 2)** After a full white frame, do 9.3 changing one glyph; if the glyph does not appear or both
  transitions invert, swap which plane carries old/new. Also try both planes = new image (no change) to confirm "no drive" for
  unchanged pixels.
- **E3 (orientation and bit order)** Send an asymmetric 'F' pattern with 0x11 = 03; record the result; choose mirror/rotation via
  0x11 ID bits and 0x01 TB so the face is upright with the bezel at the bottom; check bit order (D7 = left or right).
- **E4 (border)** Compare 3C = 05, 80, C0 (POR) for visible border flash in partial updates.
- **E5 (retention)** After 10(01) and 10(11), wake with RES#, re-run an update without rewriting RAM and see if the old image
  persists: decides whether RAM rewrite is mandatory (the plan assumes it is).
- **E6 (temperature)** Read 1B after an update (bit-banged) and compare with the board/skin temperature; capture update time at a
  cool and a warm temperature; set final BUSY timeouts.
- **E7 (ghosting vs N)** Measure after-image after 5/10/20/40 partials; pick the shipping default and record the deviation from the
  vendor's 5.
