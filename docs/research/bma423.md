## 1. Surprises and contradictions vs the brief
- **CONTRADICTION (provenance): `github.com/boschsensortec/BMA423_SensorAPI` does not exist.** The URL returns 404 (also
  `BMA423-Sensor-API`), and the Bosch Sensortec organisation's 33 public repos contain BMA400, BMA456, BMA530 and BMA580 SensorAPIs
  but **no BMA423 repo** (GitHub API listing, 2026-10-05). The SPEC's "Bosch's official BMA423 SensorAPI (BSD-3)" therefore cannot
  be fetched from Bosch today. The datasheet says the configuration file ships "in the driver available on the Bosch Sensortec
  website or from your regional support team" [BMA-DS20 4.3]; Bosch's site no longer lists the BMA423 (product page 404; the
  accelerometer overview lists only BMA400/BMA422/BMA456 among the BMA4xx parts), so even that route is unconfirmed.
- **What survives:** `github.com/sqfmi/BMA423-Sensor-API` is a fork that preserves Bosch's original commit history (commits authored
  "Bosch Sensortec <github@bosch-sensortec.com>", committer Kevin Goveas), latest tag `bma423_v2.14.13`, licence file BSD-3-Clause
  "Copyright (c) 2020 Bosch Sensortec GmbH". It is a third-party account, so authenticity rests on the commit metadata and on
  recorded checksums (section 12). Bosch's *active* official repo `BMA456_SensorAPI` (v2.29.0) has the common BMA4 core but **no BMA423
  variant files and no BMA423 config blob**; the BMA456 blob is for a different chip and must not be used.
- **Lifecycle risk (UNVERIFIABLE):** the BMA423 is absent from Bosch's current product pages. Watchy v3 ships with it; treat as
  possibly legacy and keep the driver behind an interface (BMA422/BMA456 are different feature engines, not drop-in).
- **Datasheet revisions differ.** SQFMI links rev 1.1 (May 2019, "preliminary", doc BST-BMA423-DS000-01, 129 pp.) [BMA-DS11]. The newer
  rev 2.0 (Aug 2019, BST-BMA423-DS004-00, 101 pp.) is hosted by DigiKey [BMA-DS20]. Rev 2.0 moves the feature descriptions to an
  "Application note - Wearable feature set" that I could not retrieve, so feature details below come from rev 1.1 plus the Bosch
  headers. Where they differ, rev 2.0 wins: write-to-write idle time in low-power mode is 450 us in rev 2.0 vs 1000 us in rev 1.1 (but
  rev 2.0's power-mode text still says 1000 us; use 1 ms). A third-party blog claims rev 1.1 copies are "incorrect" (not verified).
- **Sleep current is higher than the board budget assumed:** counting steps requires the accelerometer running (low-power mode,
  >= 50 Hz): **13-27 uA** from the datasheet table, Bosch marketing says "typically < 30 uA" (not in the datasheet). Suspend is only 3.5 uA but
  then nothing counts. hardware.md section 13 is updated accordingly.
- **Feature engine reset behaviour:** the whole feature engine (config upload, counter) is lost on power loss or soft reset and must be
  re-initialised; it survives MCU deep sleep because the sensor sits on the always-on 3V3 rail (hardware.md 7).

## 2. Identity, bus, wiring
- CHIP_ID (0x00) = **0x13** [BMA-DS20 quick start 3; header BMA423_CHIP_ID]. The BMA4 family ID range is 0x10-0x15 (API).
- I2C 7-bit address **0x18** (SDO=GND, as on this board); 0x19 if SDO=VDDIO [BMA-DS20 6.5]. Board: SDO to GND, CSB to 3V3 (I2C mode), SDA/SCL
  on GPIO12/11 with 10K pull-ups, INT1/INT2 on GPIO14/13, aux pins no-connect (hardware.md 7). VERIFIED.
- Supply: VDD 1.62-3.6 V, VDDIO 1.2-3.6 V; the part resets when either rail falls below minimum; power-up time <= 1 ms; boot phase makes
  the serial interface non-operational and writes are discarded while NVM loads [BMA-DS20 1, 4.1, 4.12]. Operating -40..+85 C.
- I2C: standard/fast mode plus an extended mode to 1 MHz; 7-bit only; I2C watchdog (NV_CONF.i2c_wdt_en/sel) frees a locked bus [BMA-DS20 6.5].
  With the board's 10K pull-ups, rise time is about 0.85 x 10K x C_bus (about 0.25 us at 30 pF): **use <= 400 kHz** (ASSUMED limit from the pull-ups).
- Data: 12-bit, ranges +-2/4/8/16 g (1024/512/256/128 LSB/g), ODR 12.5-1600 Hz perf mode, 0.78-400 Hz low-power mode; temperature sensor
  1 K/LSB, 23 C offset +-1 K, register 0x22 [BMA-DS20 1]. A usable board-temperature source (also for the e-paper, see ssd1681.md).

## 3. Power-up and initialisation, with timing
Datasheet procedure [BMA-DS20 3 (flow), 4.3]; VERIFIED unless marked.
1. After POR the sensor is in suspend mode, serial interface unusable until boot completes (<= 1 ms spec; wait >= 5 ms, ASSUMED margin).
2. Read CHIP_ID (0x00), expect 0x13 (communication check).
3. `PWR_CONF (0x7C) = 0x00` (adv_power_save off; it also clears fifo_self_wakeup, harmless). **Wait >= 450 us** (flow diagram uses 500 us;
   SENSORTIME_0 ticks every 39.25 us if exact timing is wanted).
4. `INIT_CTRL (0x59) = 0x00` (accept configuration file).
5. Burst-write the 6,144-byte configuration file to `FEATURES_IN (0x5E)`. Allowed as several consecutive bursts, **each burst an even number of
   bytes**. The Bosch API chunks by the host's maximum transfer length and updates two ASIC address registers 0x5B/0x5C between chunks (named
   `BMA4_RESERVED_REG_5B/5C` in the API; not described in the datasheet text). Optional: burst-read back and compare (rev 2.0: "check sensor API for
   details of timing and length").
6. `INIT_CTRL (0x59) = 0x01` (enable features). **Must be done once only per POR or soft reset.**
7. Wait until `INTERNAL_STATUS (0x2A)` bits[4:0] = **0x01** ("init_ok"): **at most 140-150 ms** (flow: non-blocking 140 ms). Other values: 0x00 not
   initialised, 0x02 init error, 0x03 invalid driver, 0x04 sensor stopped. Bits 5/6/7 flag axes-remap error, "50 Hz ODR requirement not met",
   "tap ODR requirement not met" and should be 0 after configuration.
8. After init the device is in configuration mode (adv_power_save off); switch to the wanted power mode last (section 8).
Cost estimate (derived): about 140 ms wait plus 6 KB of I2C traffic (about 160 ms at 400 kHz including overhead) at roughly 20 mA MCU current
= about 6 mC (1.7 uAh) per init. That is why init must not run every wake.
- Soft reset: `CMD (0x7E) = 0xB6`; behaves "largely equivalent to a power cycle"; all settings revert and **the init sequence must be redone**;
  delay before the interface works again is UNSPECIFIED ("following a delay"); use >= 10 ms (ASSUMED) and re-check CHIP_ID. Never during an NVM write.
- Error registers: `ERR_REG (0x02)` (fatal_err, cmd_err, error_code 1 = bad ACC_CONF, fifo_err, aux_err), `INTERNAL_ERROR (0x5F)` (int_err_1
  processing halted, int_err_2 fatal), feature `error_int_out` in `INT_STATUS_0` ("sensor stopped after a fatal error, reinitialise") [BMA-DS20 5; BMA-DS11 4.6].

## 4. Power loss vs MCU deep sleep
Rule: **register contents (and FIFO) are retained in every power configuration** [BMA-DS20 4.4]; the part only loses state when VDD/VDDIO dips below
minimum (POR) or on a soft reset. On the Watchy, VDD/VDDIO come from the LDO-fed 3V3 rail that stays on in ESP32-S3 deep sleep, so:
- **MCU deep-sleep wake (rail never dropped):** the feature engine and the step counter are alive and have kept counting. Do **not** re-upload the
  configuration; do not write INIT_CTRL again.
- **Cold boot, brown-out of the 3V3 rail, battery removal, or USB-only power loss:** the BMA423 was reset: configuration, features and counter are gone.
- **MCU reset without power loss (watchdog, panic, `esp_restart`)**: the BMA423 is still initialised; re-running the init would violate the
  once-per-POR rule. Detect, then decide.
Detection at the start of every boot/wake (cheap: three I2C reads):
1. Read `CHIP_ID` (0x00) = 0x13: bus alive. If it NACKs, the sensor is missing or in boot: retry after 5 ms, then fail soft (steps unavailable).
2. Read `INTERNAL_STATUS (0x2A)` bits[4:0]: **0x01 = features running, skip upload**; 0x00 = not initialised (power was lost), run section 3; 0x02/0x03/0x04 =
   error, soft-reset and run section 3.
3. Read `EVENT (0x1B)` bit0 `por_detected` (reset value 1, **clear-on-read**): 1 means power-up or soft reset since the last read. Read it once at every
   wake to learn whether a reset occurred even if status looks fine; log it as a "step counter lost" diagnostic. (On the first read after init it is 1:
   read and discard once after each init.)
4. Optionally read the config version (`bma423_get_config_id`, FEATURES_IN offset 0x42, major/minor masks 0x3C0/0x1F) and compare with the recorded value
   to detect a wrong blob.
Consequence for steps: after a detected power loss the sensor counter restarts at 0. Keep a firmware-side `base` (section 5) so the day total survives.

## 5. Step counter
- Hardware step counter + step detector + activity recognition live in the feature engine, run on **50 Hz** samples [BMA-DS11 4.6]. In low-power mode
  (acc_perf_mode = 0) ODR must be >= 50 Hz or flags in INTERNAL_STATUS set; in performance mode any ODR works.
- Enable: set `en_counter` in FEATURES_IN step-counter settings (feature byte offset 0x3A; per the header masks the upper byte carries 0x10 = counter, 0x08 = detector, 0x20 = activity,
  0x04 = reset-counter strobe and the low 10 bits are the watermark; the byte position is inferred from the masks, ASSUMED) [header BMA423_STEP_CNTR_OFFSET/*_MSK; BMA-DS11 4.6]. Configuration is a read-modify-write of the
  70-byte (0x46, even) FEATURES_IN block: burst-read whole block, modify, burst-write whole block [BMA-DS11 4.6, BMA423_FEATURE_SIZE = 70].
  API route: `bma423_feature_enable(BMA423_STEP_CNTR, enable, dev)` (feature bits: STEP_CNTR 0x01, STEP_ACT 0x02, WRIST_WEAR 0x04, SINGLE_TAP 0x08, DOUBLE_TAP 0x10).
- **Read:** registers `STEP_COUNTER_0..3 (0x1E..0x21)` hold a **32-bit counter** (4 x 8 bit, one 4-byte burst read; API `bma423_step_counter_output(uint32_t*)`).
  Byte significance is not stated in the datasheet text; STEP_COUNTER_0 = least significant is ASSUMED (verify: small counts appear only in byte 0).
  Reset value 0x00 on POR/soft reset. Counter wrap at 2^32 is UNSPECIFIED (irrelevant).
- **Reset:** the `reset_counter` flag clears the counter, "afterwards the value of this flag is automatically reset and counting is restarted"
  (API `bma423_reset_step_counter`); only interpreted while the counter is enabled [BMA-DS11 4.6].
- **Midnight rollover (recommended design, ASSUMED sound):** do **not** reset the hardware counter at midnight. The counter buffers a few steps internally
  ("output may be triggered between 200-210 steps" for a watermark of 200 [BMA-DS11]), so a reset can drop up to about 10 pending steps, and a reset during
  a walk is awkward. Instead store `base = counter_at_local_midnight` in RTC memory and show `today = counter - base`. Roll over by reading the counter at
  the first wake after local midnight (time/DST logic is in the host core). After a detected power loss: today_total += (counter_before_loss - base) is lost
  only to the extent unread; set `base = 0` and keep a persistent `steps_before_reset`.
- **Latency/accuracy:** the datasheet does not state update latency, accuracy or the number of steps needed before counting starts (internal buffering
  implies the first few steps may appear late): UNSPECIFIED; characterise with a counted walk (E1 in section 15).
- **Parameters (25 x 16-bit, FEATURES_IN offset 0x08..0x39):** shipped default is the **wrist preset**; no write needed for a watch ("By default, the wrist
  configuration is available for use") [BMA-DS11 4.6]. Wrist preset PARAM_1..25 as published: 301, 31700, 315, 31451, 4, 31551, 27853, 1219, 2437, 1219,
  -6420, 17932, 1, 39, 25, 150, 160, 1, 12, 15600, 256, 1, 3, 1, 14 (phone preset differs; table is for the 2019 blob: read back with
  `bma423_stepcounter_get_parameter` on the real blob and log, do not assume). To change: disable counter/detector/activity, write all 25, re-enable.
  Custom sensitivity is only supported "with the support of the field application engineer".
- **Watermark/interrupt:** `watermark_level` (10 bits, implicit x20, range 0-20460, resolution 20 steps) triggers `INT_STATUS_0.step_counter_out` every N steps
  (fires between N and N+10); 0 disables the watermark. The step-detector interrupt (one per step) is mutually exclusive with the watermark interrupt
  [BMA-DS11 4.6]. Quartz does not need step interrupts: read the counter on wake, keep watermark 0 and do not map step interrupts to INT1/INT2 (saves wakes).

## 6. Interrupt pins
Registers (VERIFIED, [BMA-DS20 4.6, 5]):
| Reg | Field | Meaning / reset |
|---|---|---|
| 0x53 INT1_IO_CTRL / 0x54 INT2_IO_CTRL | bit4 input_en, bit3 output_en, bit2 od, bit1 lvl, bit0 edge_ctrl | reset 0x00: **outputs disabled and inputs disabled** after reset. od: 0 push-pull, 1 open-drain. lvl: 0 active-low, 1 active-high. edge_ctrl: 0 level, 1 edge (documented for the pin as input) |
| 0x55 INT_LATCH | bit0 int_latch | 0 non-latched (only data-ready, FIFO full/watermark), 1 latched. **Feature interrupts support only latched mode** |
| 0x56 INT1_MAP / 0x57 INT2_MAP / 0x58 INT_MAP_DATA | mapping bits | feature outputs (INT_STATUS_0) to a pin; FIFO/data-ready (INT_STATUS_1) via INT_MAP_DATA. API `bma423_map_interrupt(line, mask, enable)` |
| 0x1C INT_STATUS_0 / 0x1D INT_STATUS_1 | status | read clears (latched mode clears status and the pin) |

- For the step-counter-only configuration leave both pins disabled (reset state) and nothing mapped: no interrupt activity, no spurious EXT1 wakes.
- For optional wrist-tilt wake: set `INT1_IO_CTRL = 0x08` (output_en, push-pull, **active-low**, level), `INT_LATCH = 0x01`, map WRIST_WEAR_INT (0x08) to INT1 (API
  mask BMA423_WRIST_WEAR_INT), include GPIO14 in the EXT1 mask with the buttons (all active-low, `ESP_EXT1_WAKEUP_ANY_LOW`). The board has no pull resistors on INT
  lines, so use push-pull (open-drain would float high only via an internal pull). **Clear `INT_STATUS_0` before going to sleep**: a latched, still-asserted line
  re-wakes the MCU immediately. Feature outputs are latched only: the condition must clear before a re-trigger.
- With INT outputs enabled and idle (push-pull active-low drives high), current is unchanged; the pin is a VDDIO (3.3 V) output [BMA-DS20 7.1].

## 7. Axis remap for the Watchy
Facts: (1) the datasheet defines the sensing axes with the package seen from the lid side: **pin 1 at upper-left gives +x up, +y left, +z toward the viewer**
[BMA-DS11 8.2 figure and orientation table, checked on all four table orientations]. (2) The remap registers (FEATURES_IN `general_settings.axes_remapping`, feature
byte offset 0x44) change the axes **seen by the features only**; DATA_8..13 and the FIFO are **not** remapped [BMA-DS11 4.6]. (3) Feature frame expected by Bosch:
X right, Y "portrait up" (12 o'clock), Z toward the wearer. (4) The wrist-tilt remap table lists eight mounting cases; the figures show the sensor as seen from the
**wearer's side** for the bottom-layer rows (verified by working out all four bottom rows geometrically) [BMA-DS11 4.6 p.37-38].
Board facts [PCB]: BMA423 on the component side (F.Cu), rotation 0, pin 1 at the top-left pad of the F.Cu view, 12 o'clock toward the top buttons (BACK/UP), display on
the opposite side (SQFMI FAQ: FPC passes through a slot to the connector; hardware.md 2). So the sensor is on the **bottom layer** as seen by the wearer, pin 1 appears
at the **upper-right** from the wearer's side: **table row 5** (bottom layer, pin#1 upper-right, portrait up):
| Feature axis | Source | Register values |
|---|---|---|
| X | +y_sensor | map_x_axis = 1, map_x_axis_sign = 0 |
| Y | +x_sensor | map_y_axis = 0, map_y_axis_sign = 0 |
| Z | -z_sensor | map_z_axis = 2, map_z_axis_sign = 1 |
Physical meaning (derived): sensor +x points to 12 o'clock, +y to 3 o'clock (wearer's right), +z away from the wearer.
Validation (do on hardware, ASSUMED correct until seen): raw DATA registers (unremapped) read about (0, 0, -1 g) watch lying face-up; (+1 g, 0, 0) held upright with 12
o'clock up; (0, +1 g, 0) with 3 o'clock up (at +-4 g: 512 LSB per g). After writing the remap, check `INTERNAL_STATUS` bit5 (axes_remap_error) = 0.
API: `bma423_set_remap_axes(struct bma423_axes_remap{x_axis,y_axis,z_axis,x_axis_sign,y_axis_sign,z_axis_sign}*)`. If wrist-tilt is not used the step counter is less
orientation-critical, but apply the remap anyway (SPEC requirement).

## 8. Power modes and current
Registers: `PWR_CONF 0x7C` (bit0 adv_power_save, bit1 fifo_self_wakeup; reset 0x03), `PWR_CTRL 0x7D` (bit2 acc_en, bit0 aux_en; reset 0), `ACC_CONF 0x40` (bit7 acc_perf_mode,
bits6:4 acc_bwp, bits3:0 acc_odr; reset 0xA8 = perf, normal filter, 100 Hz), `ACC_RANGE 0x41`. ODR codes: 0x06 = 25 Hz, 0x07 = 50 Hz, 0x08 = 100 Hz, 0x09 = 200 Hz. In
low-power mode acc_bwp selects averaging: 0 none, 1 avg2, 2 avg4, 3 avg8 ... 7 avg128 [BMA-DS20 5].
| Mode (PWR_CONF.aps / ACC_CONF.perf / PWR_CTRL.acc_en) | Current (25 C, typ) |
|---|---|
| Suspend (1 / x / 0): lowest, accelerometer off, **features do not run** | 3.5 uA |
| Low-power (1 / 0 / 1), ODR 50 Hz, no averaging | 13 uA (14 uA headline at 50 Hz) |
| Low-power, 50 Hz, avg 2 / avg 4 / avg 8 | 18 / 27 / 45 uA |
| Low-power, 25 Hz, no avg / avg 2 / avg 4 | 8 / 11 / 14 uA (below the 50 Hz minimum for features) |
| Low-power, 100 Hz / 200 Hz, no avg | 22 / 42 uA (tap needs 200 Hz) |
| Performance (x / 1 / 1) continuous | 150 uA |
Table values: rev 2.0 p.19 ("limited lab measurements, only for reference"); excludes the feature-engine's own consumption (not documented; Bosch says < 30 uA total for
the step counter, not verified).
- **Lowest-sleep configuration for step-counter-only use (decision):** `PWR_CTRL.acc_en = 1`, `PWR_CONF = 0x03` (adv_power_save on; fifo_self_wakeup default on), `ACC_CONF.acc_perf_mode = 0`,
  ODR = 50 Hz, averaging as low as step accuracy allows. Start with **`ACC_CONF = 0x17`** (avg 2, 50 Hz; the datasheet's own low-power example, 18 uA); try `0x07` (no averaging, 13 uA);
  fall back to `0x27`/performance mode if a counted walk undercounts. Accuracy per setting is UNSPECIFIED (E1). Aux interface stays disabled (`PWR_CTRL.aux_en = 0`, `IF_CONF` default).
- Low-power mode access rules: every register write needs idle time (section 11); reads of the step counter are plain reads.
- Do all configuration in configuration mode (adv_power_save = 0, fast bus rules), then write `PWR_CONF = 0x03` last.

## 9. Self-test
Procedure [BMA-DS20 4.11]: enable acc (PWR_CTRL.acc_en = 1); range +-8 g; `ACC_SELF_TEST (0x6D)` amplitude high (bit3 acc_self_test_amp = 1); ACC_CONF: 1600 Hz, continuous, normal filter; wait
> 2 ms; enable self-test positive (`0x6D` bits en = 1, sign = 1, amp = 1 = 0x0D); wait > 50 ms; read DATA_8..13; set negative sign (0x09); wait > 50 ms; read again; per axis difference must
reach **x >= 400 mg, y >= 800 mg, z >= 400 mg** (measured differences can be larger). **Reset after the test** (soft reset 0xB6) and then redo full init, which also wipes the step counter:
run the self-test only from a diagnostics command, never in normal operation; if a reset is impossible, disable interrupts, change settings, wait >= 50 ms, then re-enable. API:
`bma4_perform_accel_selftest()`, `bma4_selftest_config()`. Chip-ID, INTERNAL_STATUS = 1 and a plausible gravity vector are the cheap health checks.

## 10. Other features and cost
Feature engine inputs are 50 Hz samples; cost is the accelerometer mode (section 8), not per-feature figures (UNSPECIFIED).
| Feature | Enable (API flag / interrupt) | Notes |
|---|---|---|
| Wrist tilt ("tilt on wrist", wrist wear) | WRIST_WEAR 0x04 / BMA423_WRIST_WEAR_INT 0x08 | single-axis detection on the "portrait up" axis (needs correct remap); minimum tilt 12 degrees then about 1 s hold; fires `wrist_tilt_out`; good display-wake source |
| Any-motion / no-motion | config structs (threshold 11 bit, duration 13 bit, axes) / ANY_MOT_INT 0x20, NO_MOT_INT 0x40 | needs 50 Hz in low-power mode; usable to arm/disarm a "watch left on table" mode |
| Single / double tap | SINGLE_TAP 0x08, DOUBLE_TAP 0x10 / SINGLE_TAP_INT 0x01, DOUBLE_TAP_INT 0x10 | detects on z; sensitivity 0 (high)-7 (low); **needs ODR >= 200 Hz in low-power mode: +29 uA** (42 uA at 200 Hz) |
| Activity (walk/run/still) | STEP_ACT 0x02 (needs step counter) / ACTIVITY_INT 0x04 | read `ACTIVITY_TYPE (0x27)`; optional |
| FIFO, auxiliary magnetometer, offset compensation | not needed | skip |
Out of scope for the SPEC (no heart-rate, no BLE) but wrist tilt is the natural "raise to wake" candidate; evaluate its false-wake rate before enabling (wakes cost display power).

## 11. I2C timing and burst constraints
Table 28 of rev 2.0 [BMA-DS20 6.5] and rev 1.1 [BMA-DS11 6.5]:
| Constraint | Value |
|---|---|
| fSCL max | 1000 kHz (extended mode); standard/fast mode supported; **use <= 400 kHz on this board** (10K pull-ups) |
| Bus free time before a new transmission (tBUF) | **400 us in low-power mode**, 2 us (rev 2.0) / 1.3 us (rev 1.1) in performance/normal mode |
| Idle time between write accesses | 450 us (rev 2.0 low-power/suspend), 1000 us (rev 1.1 and rev 2.0 power-mode text); 2 us in performance mode / configuration mode |
| Idle after write before next read (suspend/low-power) | 450 us; performance mode 2 us [BMA-DS20 6.6] |
| Max burst length | UNSPECIFIED for normal registers (auto-increment); config file: any number of **even-length** bursts; the Bosch API takes the host's maximum transfer length as `read_write_len` |
| Special registers | FEATURES_IN (0x5E) is an "address trap" register: multi-byte writes do not auto-increment the I2C register address; keep every burst at address 0x5E |
Practical rule (decision): make every write while adv_power_save = 0; insert **>= 1 ms** between consecutive writes whenever adv_power_save = 1; keep >= 450 us between any
two transactions in low-power mode. Reading the 4 step-counter bytes right after MCU boot is naturally > 400 us after any prior transaction.
Direct 4-byte read at 0x1E in low-power mode is allowed by the register rules (ASSUMED; confirm against the API's own read, E2). The API's feature functions toggle
adv_power_save around feature accesses and spend about 1 ms per access (BMA4_GEN_READ_WRITE_DELAY = 1000 us), so a thin "read counter only" path saves wake time.

## 13. Deep-sleep hazards
1. **Re-running init every wake** wastes about 6 mC and violates "INIT_CTRL=0x01 once per POR/soft reset"; the Bosch `bma423_write_config_file` does not check state. Gate with INTERNAL_STATUS (section 4).
2. **Silent counter loss:** a brown-out resets the BMA423 while the MCU may survive; only EVENT.por_detected / INTERNAL_STATUS reveal it. Check every wake.
3. **Latched INT re-wakes the MCU** instantly if not cleared before sleep (EXT1 any-low); also keep INT disabled if unused.
4. **Low-power-mode write spacing** (1 ms) is easy to violate with back-to-back API calls; the config phase should run in configuration mode.
5. **Soft reset / self-test wipe the feature engine** and the counter: after either, full init and a new `base`.
6. **Stale rail assumption:** a bus lock-up at MCU reset can hold SDA low; the sensor has an I2C watchdog (NV_CONF); also toggle SCL 9 times before the first transfer after an unexpected reset (ASSUMED good practice).
7. The sensor draws the same current whether or not the MCU sleeps: the 13-27 uA is a permanent floor while step counting is on.
